# Alert rules and lifecycle

Vigira stores alert policy separately from raw telemetry. Rules are persisted in `alert_rules`; active and resolved incident state is in `alert_incidents`; each firing and recovery transition is recorded once in `alert_events`. The event table is a durable outbox boundary for a future delivery adapter. Reading `GET /api/alerts/events` does not acknowledge or deliver events. Delivery and acknowledgement belong to ENG-145.

Apply migrations in order, including `000006_telemetry_retention` before `000007_alerts`. The alert evaluator reads the existing `agent_telemetry` JSON payload and does not change its shape. Retention must preserve at least 25 hours of raw observations to support the largest accepted threshold window. Each threshold query uses only its configured sustain and grace window plus a 7-minute freshness/continuity margin, and filters to the requested metric and labels before loading observations. The evaluator rejects a rule evaluation with more than 100,000 matching observations rather than silently dropping devices or dimensions; failures are isolated to that rule so other rules still evaluate.

Authenticated local-user endpoints:

- `GET /api/alerts/rules`, `POST /api/alerts/rules`, and `POST /api/alerts/rules/{id}/disable`
- `GET /api/alerts/incidents` and `GET /api/alerts/events`

Rule `kind` is `device_unavailable`, `threshold`, `backup_failure`, or `backup_overdue`. `device_unavailable` accepts optional `deviceId`, `staleAfterSeconds` (30 seconds to 7 days), and `graceSeconds`. A missing check-in begins with device creation and fires only after the stale interval plus grace. A fresh check-in is recovery evidence.

`threshold` accepts a supported telemetry `metric`, `operator` (`gt`, `gte`, `lt`, `lte`), numeric `threshold`, optional `labels` filters (each supplied label must match), `sustainSeconds`, and `graceSeconds`. Their sum may be at most 24 hours. Incidents are scoped by device and the complete metric label set. Distinct observations must continuously satisfy the condition across the sustain interval. Firing is delayed until `sustainSeconds + graceSeconds` has elapsed from the beginning of that continuous condition. A gap longer than two minutes restarts continuity. The newest observation must be no older than five minutes. A fresh healthy observation is required to resolve an incident; a bad newest observation with an older healthy sample is pending/unknown, not recovery. Missing or unsupported metrics are not interpreted as zero or as recovery. Supported metrics currently include CPU and memory percentages, memory available bytes, and filesystem total/free bytes.

Backup monitoring requires an explicit policy identifier and cadence. Backup status is submitted through `POST /api/agent/backups/status` using the agent's bearer credential, with `deviceId`, `policyKey`, `status` (`success`, `failure`, or `running`), `observedAt`, and a unique `sourceId` for that individual status event. Retries must reuse the event ID; each later state such as `running` or `success` needs its own ID. Identical retries are idempotent. `backup_failure` requires the latest signal to be a failure; the incident remains firing across worker downtime and running signals, and only a later success is recovery evidence. `backup_overdue` fires only when a successful run exists and exceeds `intervalSeconds + graceSeconds`; without a successful run there is no overdue inference. The current agent has no backup scheduler integration, so status signals must be supplied by a future Restic integration.

The API accepts up to 1,000 persisted rules. The server evaluates enabled rules every 30 seconds. A PostgreSQL advisory lock serializes evaluations across replicas, and state changes plus outbox events commit in the same transaction. Disabled rules are not evaluated. Alert delivery, schedules, sleep/maintenance suppression, and automatic device-specific cadence discovery remain future integrations.
