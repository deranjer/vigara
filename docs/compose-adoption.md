# Compose discovery and import

## Import from the web UI

After connecting a repository and existing branch in **Compose stacks → Git settings**, choose **Import existing**. The empty stack list also offers this action after Git setup. Select an enrolled Linux device running the current agent with Docker deployment enabled. Discovery is confined to its configured `VIGIRA_COMPOSE_MANAGED_ROOT`; the installer uses the shared Compose directory containing the Vigara and Caddy subfolders.

Review each project's original folder, Docker project name, Compose files, and observed storage paths. Review Compose text for inline secrets; environment file contents are deliberately omitted. Download the recovery key and store it securely outside the server, then confirm the review and choose **Import and save to Git**. Repeat for Vigara and Caddy. Import encrypts local dotenv and required service `env_file` inputs, records the existing target, and directly pushes reviewed source files and ciphertext to Git. It does not run Compose, restart containers, or rewrite the original project files. A failed push leaves a registered encrypted draft; open it and retry Save after fixing Git access.

The original project name and directory remain authoritative for later explicit deployments, preserving relative bind paths and named-volume identities. Environment inputs are decrypted into a private validation workspace; only an explicit deployment writes the selected environment files back to their mapped original paths. Existing storage must be present. Discovery, review, preparation and confirmation all recheck source hashes and container identity/start/storage observations; changed sources or runtime require rescanning.

Imports use native age ASCII-armored ciphertext (`age-dotenv`, `.age`) with separate central-editor, target-agent, and operator-recovery recipients. No host SOPS installation is needed for these inputs. The server provisions editor/recovery identities under the persisted Git cache's `import-keys/` directory; the agent provisions its identity at `<managed-root>/.vigara-import/identity.age` unless an explicit agent identity is configured. Protect and back up those directories and the separately downloaded recovery key. Private identities are never committed to Git. Existing SOPS inputs continue to work. Automatic recipient rotation is not provided.

Builds, includes, file-based configs/secrets, optional service environment files, hooks, and shared-root interpolation needing unresolved variables require migration before import. Bind-mounted Caddy configuration remains at its existing host path; import does not copy mounted application data or configuration into Git. Keep those files backed up separately.

An imported stack displays **Imported** until Vigara records an explicit deployment. If updating Vigara or Caddy disconnects the server, the accepted host deployment continues and Vigara checks its correlated durable result after reconnecting. A missing or unfinished device result remains unknown and blocks another deployment; the server never replays the job automatically. Keep host access available for recovery. Explicit deployments with the updated agent also generate `./start.sh` and protected local environment inputs in the original project directory; see [terminal recovery](compose-recovery.md). Import alone does not create this launcher.

## Command-line discovery and preparation API

`vigira-agent compose-discover --root <directory>` creates a read-only preview of Compose applications already present on the agent host. Configure `VIGIRA_DOCKER_HOST` to a local Docker Engine endpoint (`unix://` or loopback TCP), then run the command on the machine that owns the Compose files. It uses Docker Engine `GET` requests only. It does not invoke Compose, start or stop containers, write files, or contact the Vigara server.

The preview scans standard Compose filenames and supported override filenames, then matches an application's exact `working_dir` and ordered `config_files` to Docker's Compose project/service labels. It preserves the runtime project name and working directory. The runtime inventory includes all Compose-labeled containers, including stopped containers, and reports IDs, start times, state, and storage bindings. It deliberately omits container environment, arbitrary labels, and raw inspect responses. A complete inventory is required to claim a match; mixed or unsupported states remain `runtime_unknown`. Unmatched runtime projects are reported as orphans.

The reusable `composeadoption.PrepareImport` API prepares one explicitly selected application for a later repository writer. Callers must supply an unchanged complete runtime observation, age recipients, the SOPS binary encryptor and binary-artifact validator, explicit approval for every plaintext Compose/configuration file, and an explicit interpolation input order. Each plaintext file's content hash is checked against the discovery preview. Dotenv contents are passed to SOPS in memory and returned only as ciphertext in `secrets/imported/`; serialization omits artifact content. The receipt maps each encrypted artifact to its source, format, purpose, service, Compose file, and ordering, while retaining the exact runtime observation for a fresh before/after comparison.

The receipt's `SourcePath` for a service `env_file` is its original path relative to the Compose project directory. A future runner must decrypt the mapped artifact into that same relative path inside a private project workspace before starting Compose. This preserves env-file resolution, but it does not preserve relative bind storage: `./data` in the private workspace may be a new empty directory. Relative and named storage therefore require explicit review and a verified mapping to the observed host storage before deployment; a runner must fail closed when it cannot prove that mapping. The same applies when relocating the project directory. Interpolation inputs are ordered in the receipt, with a shared root `.env` included only when explicitly selected. This preparation API does not persist Git state, record server ownership, validate the destination host, or start a stack; the web workflow described above adds repository persistence, ownership registration, and deployment integration around this preparation API.

Unsupported Compose features and secret-bearing metadata are surfaced as generic review/unsupported codes, never as copied diagnostic values. An operator must explicitly review plaintext Compose and unclassified configuration files before export; the scanner cannot prove arbitrary values are non-secret. Unsupported inputs must be resolved before preparation.
