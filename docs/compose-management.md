# Compose stack and deployment contracts (v1)

This contract defines portable Git data for Compose stacks, logical server profiles, assignments, and observed releases. Docker Compose remains the service definition language. These files describe desired configuration and its ownership; they do not perform provisioning or deployment. The current implementation issues in ENG-176–184 define adoption, secret editing, Git sync, deployment execution, and recovery separately.

## Portable repository layout

```text
compose-stacks/
  schema-version: 1 is carried by each Vigara manifest
  stacks/<stack-id>/vigara-stack.yaml
  stacks/<stack-id>/compose.yaml          # ordinary Compose
  stacks/<stack-id>/config/...            # non-secret supporting files
  stacks/<stack-id>/secrets/*.env.sops    # SOPS-encrypted dotenv files
  profiles/<profile-id>/vigara-profile.yaml
  assignments/<profile-id>/<stack-id>.yaml
  releases/<profile-id>/<stack-id>/<release-id>.yaml  # generated observation
  .sops.yaml                               # repository policy, no private keys
```

The repository root is the portability boundary. Paths in manifests are relative to their containing stack directory and may not escape it. Compose files are unmodified standard Compose files, including multiple files where explicitly listed. Vigara metadata is kept in separate `vigara-*.yaml` files so `docker compose` can consume the Compose file without an extension or wrapper. IDs are immutable lowercase slugs; display names can change. A stack may have many services. A profile groups assignments and host-level requirements; it is not a Compose project and does not imply that all its stacks deploy atomically.

Every manifest has `apiVersion: vigara.io/v1` and `kind`. JSON Schemas in `schemas/compose-management/` are normative for Vigara-owned fields. Unknown fields in a v1 Vigara manifest are rejected by a validating writer; readers may preserve unknown fields when round-tripping. Schema evolution adds optional fields; incompatible meaning or required fields use a new API version. Docker Compose fields are validated by the Compose implementation used for deployment, not redefined here. Semantic validation also rejects repeated input paths, including the same path listed twice with conflicting sensitivity or purpose. Paths are relative, nonempty, and may not contain `.` or `..` segments.

## Stack identity and Compose inputs

`stackId` is the stable Vigara identity. `projectName` is the stable Compose project identity, explicitly set in metadata and supplied to every Compose operation with `-p`. It must be retained during adoption even if it differs from the folder or stack ID. In particular, the observed `lore` folder currently uses Compose project `lore-server`; adoption must retain `lore-server`. It is not safe to infer project identity from a directory name. Project names are unique among simultaneously assigned stacks on a Docker host.

`compose.files` lists ordered Compose files; `compose.projectDirectory` is the stack root for relative path resolution. `interpolationFiles` is an ordered array: higher array index has higher precedence because Vigara passes the files to Compose in that order, with later files overriding earlier files; there is no separate numeric precedence field. Duplicate paths are invalid. Compose interpolation is performed by Docker Compose using an explicit, controlled interpolation environment. The deployment runner starts with an empty environment and admits only the documented Compose control-variable allowlist; it never inherits ambient Vigara server variables. Each `interpolationFiles` entry is decrypted/materialized to a private temporary file before invocation. For imports that depended on the observed root-shared `.env`, record its values as an encrypted shared interpolation input on each affected stack in the order observed in the original invocation. This preserves the discovered dependency without claiming that Compose automatically merges parent `.env` files. Never silently remove that input or substitute an empty value. The operator must explicitly confirm the resulting resolved configuration before the first managed deployment.

Compose `env_file` remains service-container environment input. `environment` on the service overrides `env_file`, including an explicitly empty value. Host shell values and interpolation files only reach the container when the Compose model uses interpolation or pass-through syntax; they are not automatically injected into every service. Compose `--env-file` inputs govern interpolation, not service `env_file`. The `docker compose run -e` override is excluded from managed deployments because it makes the saved release non-reproducible. Compose interpolation follows Docker's shell > explicit `--env-file` list (later files override earlier files) > default project `.env` behavior, but Vigara always supplies its enumerated input list and disables ambient shell leakage except for a minimal allowlist of Compose control variables. Service env precedence follows Compose: CLI `run -e` (not used), interpolated `environment`/`env_file`, service `environment`, service `env_file`, then image `ENV`.

Secret dotenv inputs are SOPS-encrypted at rest and decrypted only into a mode-0600 temporary deployment workspace. The workspace is removed after the Compose process exits, including failures; plaintext must not enter API responses, logs, diagnostics, job output, Git, or release records. Existing imported `.env` files are encrypted in full initially, including non-secret values, to preserve exact behavior. A later UI edit may classify values, but a classification change is an explicit saved revision. Applications supporting file-based secrets should use them; ordinary environment values remain supported for compatibility.

## Profiles, assignments, and ownership fencing

A server profile is a logical, replaceable role, not a machine identity. Its `profileId` and assigned stack IDs survive hardware replacement. A profile contains only declarations for requirements (networks, storage mounts, and startup dependencies); it does not create them. Paths and network names must be satisfied by operator provisioning before a deployment can proceed. A profile may collect independently deployable stacks.

An assignment is one stack's desired placement on one logical profile, with an environment selector and a monotonically increasing `ownershipEpoch`. The single `ownership.mode` field controls multiplicity. The same stack may have multiple assignments only when `ownership.mode: stateless` is explicit, each has a distinct `replicaKey`, and assignment IDs, project names, and target profiles are distinct. The default is `exclusive`; stateful stacks have exactly one active owner. A second concurrent assignment of an exclusive stack is invalid. A reassignment is a fenced transfer between distinct enrolled agents: acquire a server-side transfer lock, stop or otherwise fence the previous owner, confirm its lease/agent is revoked and unable to execute, increment the epoch by one, write the new profile binding and Git commit, then allow deployment on the new owner. Lease expiry or a missed heartbeat alone is never fencing. Loss of the old host is not proof that it cannot return; recovery requires an explicit operator fencing decision (power/network isolation or documented equivalent). The agent and every job are bound to assignment ID, profile ID, and epoch. Stale epochs are rejected. Git history records the assignment epoch; database audit records both agents, old/new epoch, actor, fencing evidence, and transition. Deleting/replacing a machine never silently transfers ownership.

`profileId` is separate from enrolled `agentId`. The runtime binding in the database maps a profile to one active enrolled agent at an epoch, with status and last heartbeat. That binding is operational state and is not copied into portable Git. The Git assignment is intent; enrollment credentials remain in the existing enrollment system and are never committed. Replacing hardware enrolls a new agent and updates the DB binding only after the ownership transfer commits. Profile/assignment changes in Git alone cannot grant an agent permission.

## Git authority, drafts, saves, and deployments

Git is authoritative for saved stack definitions, non-secret configuration, encrypted secrets, profiles, and assignments. The database is authoritative for agent enrollment/bindings, drafts, sync state, jobs/leases, runtime observations, and audit/deployment history. Database indexes of Git objects are caches and can be rebuilt. A release record is an observation linked to its immutable Git commit; it never becomes a second editable source of desired configuration.

The UI edits a local draft against a recorded base commit and file hashes. Plaintext secret edits exist only in request memory and are encrypted before any persistence. A persisted draft contains the encrypted SOPS file plus non-secret metadata; database storage must encrypt that content at rest and must never index, log, or return secret values. **Save** validates Compose and Vigara manifests, encrypts secret files, detects remote changes, then creates and pushes a Git commit. A save is successful only after the remote confirms the commit; otherwise it is `pendingPush` and cannot be deployed. Conflicts are surfaced with the base/local/remote revisions and require explicit resolution; there is no last-write-wins. Changes arriving from Git update the indexed saved revision but do not overwrite a dirty draft. **Deploy** selects an already-pushed commit (or explicit stack subtree revision), shows a plan, and then submits a durable job. It never saves a draft implicitly and never deploys a pending push. Job retries remain pinned to the selected commit and epoch. A later commit does not mutate an in-flight deployment.

Each deployment report includes assignment/profile/epoch, stack ID, stable Compose `projectName`, requested Git commit and configuration revision (SHA-256 of the canonical Vigara manifest plus referenced Compose/config files), resolved image references and immutable `sha256` digests, agent ID, job ID, start/end times, outcome, and observed Compose project/service state. Git commit IDs are exactly 40 or 64 lowercase hexadecimal characters (SHA-1 or SHA-256 repositories). Mutable tags can be recorded for explanation but do not identify an image. The release ID is lowercase SHA-256 of compact, key-sorted canonical JSON with `assignmentId`, `gitCommit`, `configurationRevision`, `serviceImages` (sorted `[service, digest]` pairs), and `jobId`. A failed attempt is still recorded and never overwritten. The DB holds the operational release event; an optional release YAML under `releases/` is a portable, append-only observation and must not contain secrets or machine credentials.

External Git changes are fetched and validated before becoming the current saved revision. Invalid changes remain visible as rejected remote revisions and cannot deploy. Push races trigger a fetch/rebase-or-merge workflow with explicit conflict resolution; Vigara never force-pushes over a remote update.

## Secret-editor trust and recovery

The central Vigara server is trusted to decrypt and edit secrets. It therefore needs an editor age identity whose private key is accessible only to the Vigara service account through a protected file or OS secret facility. Do not return that identity or plaintext to browsers. Editors may send a value over the authenticated session; the API handles it only in memory and writes an encrypted SOPS file. The central identity is a high-impact trust boundary: its compromise exposes every repository secret encrypted to it.

Encrypt deployment secret files to three independently managed recipient classes: central editor, target agent identity, and operator recovery identity. `secretRecipientRefs` contains opaque inventory references to those recipient records, never private keys or literal recipient secrets. The `target-agent` reference resolves to the enrolled agent bound to the assigned profile and current epoch. Use SOPS with age recipients and keep only public recipient strings and SOPS metadata in Git. The target agent identity is unique per agent, protected in the agent service context with restrictive OS ACL/mode; do not reuse it as a Vigara server or recovery key. Agent decryption authority is limited operationally by the deployment job's assignment, epoch, stack, and allowed paths. The target still receives plaintext for environment-based applications, so Docker host access remains effectively root-equivalent and must be explicitly granted by an operator. Never expose secret values to a telemetry or diagnostics capability.

Recovery identities are generated and escrowed independently of Vigara and the target host, with at least one tested offline copy under operator custody. Recovery keys are not stored in the same Git remote, database, or host being recovered. The editor key is backed up separately from the target and operator recovery identities. Initial provisioning, ACLs, offline backup, restore drills, recipient inventory, rotation, and revocation are prerequisites owned by the operator; this contract does not generate or distribute live keys. Rotation adds new recipients and re-encrypts in a saved commit before old recipients are removed; confirm all intended recovery paths can decrypt the new revision. Revocation cannot make previously copied ciphertext or plaintext disappear.

SOPS provides file encryption and structured editing, not Git authentication, authorization, or deployment approval. Protect Git credentials separately with least privilege: read access for fetch/deploy, write access only for save, no force-push/delete permissions. User authentication, agent enrollment, Git credential, editor identity, agent identity, and recovery identity are distinct credentials.

## Existing observed inventory and boundaries

ENG-174 read-only discovery on `derajnet-server` found 44 application folders, 45 Compose files including root, 42 running Compose projects, and 29 application-local `.env` files. The root `.env` has 45 assignments and appears to supply variables referenced by phpmyadmin, portainer, radarr, sonarr, and trilium. This is a dependency to preserve during adoption; actual Compose launch inheritance remains unverified. Existing external networks, host networking, device access, bind mounts, and relative bind mounts require explicit profile requirements and operator review. Counts describe declarations, not unique resources. No values were read, no host was changed, and no second-server inventory was available. Examples below are synthetic and do not assert an observed second host.

Linux/Docker/storage provisioning and backups remain prerequisites. No automatic deployment on push, generic provisioning, bare-metal recovery, transactional Compose rollout, or database migration rollback is promised. A Compose release rollback does not reverse application data migrations.
